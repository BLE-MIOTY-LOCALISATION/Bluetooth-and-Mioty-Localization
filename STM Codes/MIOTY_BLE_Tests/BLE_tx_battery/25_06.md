# BLE Battery Optimizer Implementation Summary - 2026-06-25

This document details the issues resolved, clock re-configurations, and code corrections made on **2026-06-25** to achieve a fully functional, ultra-low-power standalone BLE Beacon on the target hardware.

---

## 1. Summary of Bug Fixes & Code Corrections

### A. Resolved 'alarm_fired' Undeclared Compile Error
* **The Problem:** The compiler halted with `error: 'alarm_fired' undeclared (first use in this function)` in `RTC_Alarm_IRQHandler` at line 466.
* **The Fix:** Declared `volatile uint8_t alarm_fired = 0;` in the Private Variables (PV) user code block in `main.c`. This resolved the compiler error and allowed the project to build cleanly.

### B. Populated the Empty Main Loop
* **The Problem:** The `while (1)` loop in `main()` was completely empty, meaning the MCU did not execute the beacon transmission or enter low-power Stop Mode.
* **The Fix:** Populated the loop to execute the low-power wakeup-transmission-sleep cycle:
  ```c
  while (1)
  {
    // 1. Transmit BLE beacon on all 3 advertising channels
    SX1280_SendBLEBeacon();

    // 2. Shut down peripherals, flash LED, and enter Stop Mode (wakes up in 1s)
    STM32_EnterStopMode();
  }
  ```

### C. Initialised the LORA_NRST Pin
* **The Problem:** The `LORA_NRST_Pin` (`PA3`) was used to reset the Semtech SX1280 on boot and pull-up lock during sleep, but it was never initialized as a GPIO output in `MX_GPIO_Init()`. It was left floating in an input state, which risked placing the radio in a continuous hardware reset.
* **The Fix:** Configured `PA3` as `GPIO_MODE_OUTPUT_PP` (Output Push-Pull) in `MX_GPIO_Init()` alongside `LORA_NSS_Pin` (`PA4`), and initialized both pins to `GPIO_PIN_SET` (HIGH) by default.

### D. Corrected Active-High LED Polarity & Sleep Desync
* **The Problem:** The onboard LED uses **active-high** polarity (writing `SET` turns it ON, writing `RESET` turns it OFF). Because the previous code wrote `SET` to turn it OFF:
  1. The LED was left ON/bright after the boot verification sequence completed.
  2. Inside `STM32_EnterStopMode()`, the LED went OFF for 10ms and then turned back ON/bright right before the MCU went to sleep. This caused the LED to consume continuous current ($\approx 3\text{ mA}$) during the 990ms sleep phase, defeating the low-power optimization.
* **The Fix:** Swapped the logic states for the LED across `main.c`:
  * **Verify Init Finish:** We write `RESET` to turn the LED OFF after boot diagnostics.
  * **Stop Mode Flash:** Inside `STM32_EnterStopMode()`, we write `SET` (ON) for 10ms, and write `RESET` (OFF) before sleeping.
  * *Result:* The LED is now completely OFF during the active transmission and Stop Mode sleep phases, flashing briefly for 10ms only once per second.

## 2. Low-Power Clock Optimization: LSI to LSE Switch

* **What we did:** Switched the RTC clock source from the internal **LSI RC oscillator** ($\approx 40\text{ kHz}$) to the highly accurate external **LSE watch crystal** ($32.768\text{ kHz}$).
* **The Configurations:**
  * Enabled the LSE oscillator (`RCC_OSCILLATORTYPE_LSE`, `RCC_LSE_ON`) in `RTC_Init_LowPower()`.
  * Routed `RCC_RTCCLKSOURCE_LSE` to the RTC clock multiplexer.
  * Adjusted the RTC Prescaler division factor from `39999` to **`32767`** ($32768 - 1$) to generate an exact **1 Hz** tick from the $32.768\text{ kHz}$ crystal.
* **Benefits:** 
  * **Precision:** The LSE crystal does not drift with temperature or battery voltage fluctuations, ensuring the beacon wakes up and advertises at exactly $1.000\text{ second}$ intervals.
  * **Power Efficiency:** The external crystal driver consumes less than $1\ \mu\text{A}$ in Stop Mode, compared to the internal RC oscillator's current draw.

## 3. Register Read Safety: RSF Flag Synchronization

* **The Problem:** Waking up from Stop Mode halts and restarts the APB peripheral clock. Reading the RTC counters (`RTC_CNTH`/`CNTL`) immediately after wakeup without synchronization can load corrupted, garbage, or stale values into the code, breaking the alarm scheduler.
* **The Fix:** Added a Register Synchronized Flag (`RSF`) clear-and-wait loop at the beginning of `RTC_SetAlarm_1s()`:
  ```c
  void RTC_SetAlarm_1s(void) {
    // Clear Register Synchronized Flag (RSF) and wait for synchronization (critical after wakeup)
    WRITE_REG(RTC->CRL, (uint32_t)~RTC_CRL_RSF);
    while ((RTC->CRL & RTC_CRL_RSF) == 0) {
    }
  ```
* **Why it works:** This forces the APB interface to wait until it is synchronized with the RTC core clock domain before reading the counter, guaranteeing that `cnt` represents the true current RTC time.

## 4. Hardware Diagnostics: Board Mismatch & Antenna Routing Issue

### A. The Symptom
* **Board 1 (No Coaxial Slot):** Works perfectly at both `+13 dBm` and `0 dBm` (packets received).
* **Board 2 (Coaxial Slot Soldered, Magnetometer Added):** Runs the software cycle normally (LED flashes at 10ms/1s), but packets are only received when running the old code (`2_ble_mioty_ble_tx_ble_working`). It fails to transmit packets on-air with the new `BLE_tx_battery` code.

### B. Technical Root Cause (Antenna Routing & RF Leakage)
1. **Unpopulated PCB Antenna Path (`C24`):**
   * On Board 2, the coaxial connector `J1` is populated, but capacitor `C24` is unpopulated (open-circuit). This physically disconnects the onboard PCB trace antenna (`AE1`) from the RF output.
   * If no external 2.4 GHz antenna is plugged into the coaxial slot `J1`, the transceiver has **no physical antenna/radiator** connected to it.
2. **RF Output Power Difference (+13 dBm vs. 0 dBm):**
   * **Old Code (+13 dBm / 20 mW):** Because the transmit power is extremely high, the RF energy "leaks" directly from the board's traces and open coaxial pins. This weak spurious leakage is strong enough to be detected by a nearby receiver (within 1–2 meters).
   * **New Code (0 dBm / 1 mW):** The transmit power is reduced 20-fold to optimize battery life. At this low power, the trace/connector leakage is too weak to reach the receiver's threshold, resulting in zero packets detected.

### C. Resolution & Testing Steps
* **Verification Test:** Temporarily set the TX power in `SX1280_InitBLE()` back to `+13 dBm` (change `0x12` to `0x1F` in the `0x8E` command) to confirm that the receiver starts picking up Board 2's packets.
* **Production Fix:** Solder an external 2.4 GHz antenna to the coaxial connector `J1`, or solder a matching capacitor/jumper on `C24` to route the RF signal to the onboard PCB trace antenna (`AE1`).
